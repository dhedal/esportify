1. Analyse des Besoins

1.1 Résumé du projet

Esportify est une startup innovante spécialisée dans le e-sport, fondée en 2021 en France. Jusqu'à présent, la gestion des événements était réalisée manuellement à l'aide de fichiers Excel et d'un CMS WordPress, entraînant des limitations opérationnelles.

L'objectif du projet est de développer une plateforme web complète permettant :

  • Aux joueurs de s’inscrire et participer aux compétitions.
  • Aux organisateurs de créer et gérer des événements.
  • Aux administrateurs de valider et modérer les événements et utilisateurs.

Cette plateforme vise à automatiser la gestion des événements, améliorer l’expérience utilisateur et renforcer l’accessibilité pour Esportify.

1.2 Cahier des charges / Expression du besoin

  • Objectifs du projet : Digitaliser la gestion des événements e-sport afin de remplacer les outils manuels existants, offrir une interface intuitive et sécurisée, et garantir une gestion fluide des inscriptions, validations et scores.
  • Fonctionnalités principales :
    • Page d’accueil avec présentation et événements à venir.
    • Système d’authentification (Joueur, Organisateur, Administrateur).
    • Gestion des événements : création, inscription, validation, historique.
    • Modération des utilisateurs et événements par les administrateurs.
    • Fil de discussion asynchrone (optionnel) pour la communication entre joueurs.
    • Tableau de bord organisateur et administrateur.
  • Contraintes techniques et fonctionnelles :
    • Développement avec Spring Boot pour le backend.
    • Développement avec Thymeleaf, Javascript et Bootstrap css pour le frontend.
    • Base de données MySQL avec gestion des relations entre utilisateurs et événements.
    • Sécurisation via Spring Security.
    • Interface responsive et accessible (Desktop & Mobile).
    • Filtrage dynamique des événements (requêtes asynchrones en AJAX).

2. Spécifications Techniques

2.1 Technologies utilisées et justification

Le projet repose sur un socle technologique robuste et éprouvé :

  • Spring Boot : Choisi pour sa rapidité de développement et son intégration simplifiée avec d'autres outils du Spring Ecosystem.
  • Spring Data JPA : Utilisé pour l'interaction avec la base de données MySQL, garantissant une gestion optimisée des transactions et évitant les injections SQL.
  • Thymeleaf : Intégré en tant que moteur de templates pour le rendu côté serveur, permettant une séparation claire entre logique et présentation.
  • MySQL : Base de données relationnelle choisie pour sa stabilité et son support robuste des transactions.
  • JavaScript : Utilisé pour gérer les interactions dynamiques côté client et améliorer l'expérience utilisateur.
  • Bootstrap CSS : Employé pour structurer et styliser l’interface utilisateur de manière responsive et ergonomique.

2.2 Mise en place de l’environnement de travail

Le développement repose sur une architecture modulaire et des outils adaptés :

  • IntelliJ IDEA : Environnement de développement choisi pour sa compatibilité avec Spring Boot et ses fonctionnalités avancées.
  • GitHub : Gestion de version avec Git Flow pour assurer un workflow structuré et collaboratif.
  • MySQL Workbench : Outil utilisé pour la gestion et la visualisation des bases de données MySQL.
  • Bootstrap CSS : Utilisé pour concevoir une interface utilisateur responsive et moderne.
  • JavaScript (AJAX) : Implémentation de requêtes asynchrones pour améliorer l’interactivité et réduire les rechargements de page.

2.3 Mécanismes de sécurité

  • Sécurité des formulaires : Validation des entrées utilisateur via JavaScript et Spring Boot Validation pour assurer la conformité des données avant et après soumission des données.
  • Sécurité du back-end : Spring Security est utilisé pour gérer l'authentification et l'autorisation avec un AuthenticationManager. Les accès sont définis via HttpSecurity avec des règles spécifiques.
  • Gestion des sessions : Configuration avec SessionCreationPolicy.IF_REQUIRED pour maintenir les sessions uniquement si nécessaire.
  • Accès aux URLs : Les requêtes sont sécurisées avec Spring Security :
    • Les endpoints publics sont définis dans requestMatchersPermitAll() et accessibles sans authentification.
    • Les endpoints nécessitant une authentification sont définis dans requestMatchersAuthenticated().
    • Tout autre endpoint est protégé par défaut.
  • Gestion des déconnexions : Implémentation d'un point de sortie sécurisé via logout, supprimant les cookies et invalidant la session après déconnexion.
  • Sécurité du front-end : Protection contre les attaques XSS avec l’échappement des données et validation côté client avec JavaScript.

2.4 Veille technologique sur les vulnérabilités de sécurité

  • Problème rencontré : Configuration des autorisations d'accès aux URLs dans Spring Security.
  • Extrait d’une source en anglais : "Modern applications often serve both public and secured endpoints. Applying a custom Spring Security filter globally can lead to unnecessary processing for public endpoints. To address this, we can target the filter specifically to secured endpoints by using Spring Security’s SecurityFilterChain and RequestMatcher."
  • Traduction en français :
    "Les applications modernes servent souvent à la fois des endpoints publics et sécurisés. Pour résoudre ce problème, nous pouvons cibler le filtre spécifiquement sur les endpoints sécurisés en utilisant SecurityFilterChain et RequestMatcher de Spring Security."

3. Recherche

3.1 Situation de travail nécessitant une recherche en anglais

Lors du développement de la plateforme, j'ai rencontré un problème lié à la validation des données dans les classes services. J'utilisais l’ancienne version javax.validation au lieu de jakarta.validation, ce qui empêchait les annotations de validation de fonctionner correctement. Après plusieurs tentatives, j'ai découvert que cette migration était nécessaire en raison des changements apportés dans Spring Boot 3. Cela a nécessité une mise à jour des dépendances et l’adaptation des annotations pour garantir le bon fonctionnement des validations.

3.2 Source en anglais et traduction

  • Extrait d’une source en anglais :
    "javax.validation has been replaced by jakarta.validation in Spring Boot 3. If validation annotations are not working in your service classes, check your dependencies and ensure you're using the correct Jakarta packages instead of Javax."
  • Traduction en français :
    "javax.validation a été remplacé par jakarta.validation dans Spring Boot 3. Si les annotations de validation ne fonctionnent pas dans vos classes de service, vérifiez vos dépendances et assurez-vous d’utiliser les bons packages Jakarta au lieu de Javax."
  • Source : Stack Overflow - Migration javax.validation vers jakarta.validation

4. Conclusion

Ce projet a permis d'automatiser la gestion des événements e-sport en fournissant une solution web complète et intuitive. La transition depuis un système manuel (Excel, WordPress) vers une plateforme sécurisée et dynamique a été un véritable challenge technique et organisationnel.

Les principales difficultés rencontrées concernaient l’implémentation des rôles dynamiques et la sécurisation des accès. Grâce à l’utilisation de Spring Security et de bonnes pratiques de développement, ces problèmes ont été résolus efficacement.

Les perspectives d'amélioration incluent l'ajout d'un système de notifications en temps réel, une meilleure gestion des statistiques des joueurs, et l’intégration d’une API tierce pour enrichir l’expérience utilisateur.

4. Modèle Conceptuel de Données (MCD)

Le Modèle Conceptuel de Données (MCD) ci-dessous illustre la structure des entités et leurs relations dans l’application Esportify.

4.1 Description des entités

  • user : Stocke les informations des utilisateurs (email, mot de passe, pseudo, statut).
  • event : Contient les événements organisés (titre, description, dates, statut, organisateur).
  • event_participant : Permet de gérer les utilisateurs inscrits aux événements.
  • ask : Gère les demandes spécifiques des utilisateurs (ex. demande pour devenir organisateur).
  • event_image : Stocke les images associées à chaque événement.

4.2 Relations entre les entités

  • Un utilisateur (user) peut organiser plusieurs événements (event).
  • Un utilisateur (user) peut s'inscrire à plusieurs événements via la table event_participant.
  • Un événement (event) peut avoir plusieurs images via la table event_image.
  • Un utilisateur (user) peut soumettre des demandes via la table ask.

6. Déploiement de l’application

L’application est déployée avec Docker en orchestrant les services Spring Boot et MySQL, permettant ainsi une exécution isolée et reproductible sur différents environnements.

6.1 Configuration des conteneurs

Le déploiement repose sur deux services principaux :

  • Un conteneur MySQL pour gérer la base de données et assurer la persistance des données.
  • Un conteneur Spring Boot contenant l’application et son environnement d’exécution Java.

6.2 Étapes de déploiement

Les étapes pour exécuter l'application avec Docker sont les suivantes :

  • Créer un fichier Dockerfile pour construire l’image de l’application avec OpenJDK 21.
  • Créer un fichier docker-compose.yml pour orchestrer la base de données et l’application.
  • Définir un fichier .env pour stocker les variables sensibles comme les identifiants de base de données.
  • Exécuter la commande docker-compose up --build -d pour construire et démarrer les conteneurs.
  • Vérifier que l’application fonctionne en accédant à http://localhost:9090 (ou autre port configuré).
  • Utiliser docker-compose logs -f app pour consulter les logs de l’application et détecter d’éventuelles erreurs.

6.3 Gestion des mises à jour et maintenance

Pour déployer une nouvelle version de l’application sans interrompre le service :

  • Mettre à jour le code source et recompiler l’application avec mvn clean package -DskipTests.
  • Redémarrer proprement les conteneurs avec docker-compose down puis docker-compose up --build -d.
  • Vérifier l’état des conteneurs avec docker ps et surveiller les logs en cas de problème.

6.4 Résolution des problèmes courants

En cas de dysfonctionnement, voici quelques vérifications et actions possibles :

  • Port 9090 occupé : Vérifier les processus avec netstat -ano | findstr :9090 et tuer le processus en conflit avec taskkill /F /PID [PID].
  • Base de données inaccessible : Vérifier que MySQL est bien en cours d’exécution avec docker-compose logs -f db.
  • Variables d’environnement non chargées : Vérifier leur présence avec docker-compose exec app printenv | grep DB_.
  • Erreur d’accès au fichier JAR : Vérifier que le fichier est bien généré et copié dans le conteneur avec ls -lh /app/target/.
